# Application architecture

- Keep customer calculations and narratives in the deterministic engine; routes consume the same review model so dashboard and exports agree.
- Derive contextual insight and site tags through one shared display helper so cards, pills and exports use the same labels.
- Require operator uploads for active data; never load bundled fixtures or merge omitted tables from a previous dataset. Uploaded data, avatars and preferences remain browser-local and must be labelled accordingly.
- Build PDF and editable PowerPoint from one renderer-neutral deck; initialize the legacy archive scheduler with native microtasks and run pdf.js parsing in-page (not in a Worker), because cross-thread messaging stalls in embedded previews.
- Derive the deck only from the shared Recap (plus optional KAM notes and sources) and lay every slide out once in `slide-layout.ts` as renderer-neutral operations painted by the preview, PowerPoint and PDF; measure text before writing because PowerPoint's shrink flag does not fit text until edited.
- Normalize generated PowerPoint packages before download (existing parts with valid MIME types, XML-safe text, schema child order, one leading paragraph-properties element per paragraph); retain STORE ZIP entries to match the confirmed-working reference, but do not treat ZIP compression or schema validation as proof of Windows PowerPoint compatibility.
- Deliver PowerPoint only after server-side CloudConvert Office conversion through ODP back to PPTX; keep connector keys server-only, delete conversion jobs after reading results, never fall back silently to unconverted files, and retain a ready-file download for browsers requiring a fresh user gesture.
- Use manual redirects and reject non-success statuses for conversion uploads/downloads; the hosted runtime does not support fetch redirect mode "error" and must not follow unvalidated destinations.
- Start PowerPoint preparation in the account shell and share a bounded session-memory cache keyed by deck content and palette with the export page; serialize conversions, debounce edits, retain failures until explicit retry, and download only the matching ready version.
- Switch the active person only from the shared header or a person's Generate report action (which also requests that person's matching PowerPoint download); editing a person saves without switching the active report.
- Edit profile locations using the studio's shared country/city options and resolve selected locations into country metadata; preserve city selections so editing does not widen report scope.
- Derive profile-interest weights with one deterministic helper used by generation, the account model and profile previews; derive country scope from the active avatar, not independent saved filters.
- The report studio (`/`) is the entry: up to three uploads merged by `merge-files.ts` → company/role/location audience built deterministically by `audience.ts` → generate → Recap; optional web research runs in the background and its rules stay source-attributed and reach the engine only through `regulatory.ts`.
- Build Recap chapters in the deterministic `recap.ts` engine from the shared `buildReview` bundle; components only render and animate them, so studio preview, Recap and dashboard agree.
- Recap scenes render their final state and expose data-* animation hooks; GSAP ScrollTrigger timelines are built in one `useGSAP` scope and start only after the browser motion preference is known, preventing pinned DOM from being removed before cleanup; reduced motion renders a static stacked story.
- App visuals use project-owned Lindström tokens and `src/components/ui` primitives; Ventura components are used only for behaviour (menus, dialogs, inputs), never restyled inside the vendor subtree. The rehearsal scorecard uses an app-owned stacked chart and score rows so its layout fits the sidebar independently of viewport width.
- Treat the attached Ventura subtree as immutable vendor code; exclude unrelated library pages from root TypeScript discovery while retaining checks on imported components.
- Keep content pages in TanStack file routes with unique metadata; account layout owns shared controls and renders an Outlet.
- Apply company-brand tokens at the document level for portal consistency; keep palettes and validation browser-safe and company overrides in customer settings, so changing customers also changes portaled controls.
- Keep the dashboard guide in the shared account shell and navigate existing content routes; use data-tour targets for contextual highlighting without changing review state.
- Load Logo.dev logos only from explicit company website/domain fields or per-company browser settings, never guessed company-name domains; use its publishable client key and a neutral unavailable state.
- Rehearsal voicing uses the server-only ElevenLabs connector through /api/voice; the shared speaker hook owns cancellation and audio cleanup so mute, restart and navigation stop playback without exposing credentials.
- Research new people server-side through `/api/person` with a strict schema after converting their files to text in the browser; fetch portraits from live-search pages or the operator's supplied public LinkedIn profile, verify LinkedIn CDN images against that page, downscale before browser storage, and let the AI choose Recap questions 4-5 only from `RECAP_TOPIC_CATALOG` so the deterministic engine still computes every figure. Photo-only retries must not change report interests or active person.
- Recap elements link through `RecapTarget` to stable dashboard anchors (`id` + `data-deep-link`); `useDeepLinkFocus` waits for, scrolls to and briefly highlights the target.
- The header's New report confirms, then clears people and report settings through `resetReports` while keeping uploaded data, company brand/domain and assumptions.
